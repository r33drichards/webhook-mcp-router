# Bounded official-source outbound feasibility review

## Finding

No supported adapter or build target was verified for **Go 1.27.3 + official Go MCP SDK + embedded Go OPA + managed Wasmer WCGI/Edge** that makes the current standard `net/http` client perform real outbound networking. This is a bounded negative finding, not proof that a custom integration is impossible. No tooling was installed, network denial retried, alternative stack implemented, or deployment performed in this pass.

## What the Wasmer sources establish

1. [Wasmer's own WASIX guide](https://docs.wasmer.io/runtime/wasix/) explicitly distinguishes Go's single-threaded `wasip1` port from WASIX and directs socket/subprocess-dependent Go programs toward another design or language. The [language guides](https://www.wasix.org/docs/developer-guide/) document Rust/C toolchains, not a supported Go WASIX target. Changing Wasmer runtime permissions does not change the guest's imported ABI or Go net implementation.
2. [Edge architecture](https://docs.wasmer.io/edge/architecture/) exposes its network overlay to WASIX guests. [Deployment modes](https://docs.wasmer.io/edge/learn/deployment-modes/) document WCGI's incoming environment/stdin/stdout mapping separately. Neither source documents automatic Go outbound interception.
3. Wasmer **does implement host networking**. Version 7.5.0 includes [sock_connect](https://github.com/wasmerio/wasmer/blob/v7.5.0/lib/wasix/src/syscalls/wasix/sock_connect.rs), using the configured network and checking socket-connect rights, and [sock_open](https://github.com/wasmerio/wasmer/blob/v7.5.0/lib/wasix/src/syscalls/wasix/sock_open.rs). These require compatible guest calls; they are not a Go net/http adapter.
4. Wasmer's [http_dynamic_size example](https://github.com/wasmerio/wasmer/blob/v7.5.0/examples/http_dynamic_size.rs) implements a custom `env.http_get` import in a **native embedding host**. Its [ReqwestHttpClient](https://github.com/wasmerio/wasmer/blob/v7.5.0/lib/wasix/src/http/reqwest.rs) is runtime-side Rust code. Neither establishes that a managed WCGI app can install arbitrary imports or that Go net/http uses them. The [wasmer-go import example](https://github.com/wasmerio/wasmer-go/blob/master/examples/example_imports_function_test.go) likewise shows a Go **host embedding Wasmer**, not a Go guest gaining sockets. Inspected 7.5.0 repository tree/examples did not supply a Go guest networking adapter.
5. A supported outbound example exists for **Rust WASIX**: [WASIX with Reqwest](https://www.wasix.org/docs/language-guide/rust/tutorials/wasix-reqwest/) demonstrates an outbound proxy; the [Axum guide](https://www.wasix.org/docs/language-guide/rust/tutorials/wasix-axum/) documents Wasmer execution and Edge deployment. These are documented alternatives, not tests run by this project. Required crate forks/toolchain versions must be pinned and tested before use.

## Two concrete alternatives

| Alternative | Preserved | Change and tradeoff | User decision required |
| --- | --- | --- | --- |
| **A. One native Go Linux service, hosted as a container or ordinary process** | Official Go MCP SDK, in-process native Go OPA, webhook receiver fork, normal TLS/HTTP and DB drivers; Nix remains usable | Gives up all-in-Wasmer/Edge deployment. Existing native tests are useful evidence but do not prove a new provider's persistence or E2E. Fewest changes and clearest path to the requested functional POC. | Choose hosting/account and approve any resource/cost prerequisites before deployment. Recommend this if the working POC matters more than Wasmer hosting. |
| **B. Rust WASIX Edge frontend plus native Go backend** | Edge presence; official SDK and native Go OPA stay together in the backend; documented Rust Reqwest/Axum networking path at the frontend | Two services and an authenticated hop; violates the current one-service/all-Wasmer preference. The native Go backend owns registration storage, verification and callback delivery. The Edge frontend is a bounded ingress proxy, not a replacement OPA implementation. Integration and costs remain untested. | Explicitly accept the service split and choose/authorize backend hosting. Do not implement this silently as if it were the original design. |

A custom self-hosted Wasmer embedding host with narrow HTTP imports is another research direction demonstrated in principle by Wasmer's import example. It would require a Go transport adapter, memory/ABI bounds, TLS/SSRF/time-limit handling, and separate execution proof. It is **not** a verified managed-Edge solution and is not recommended as the next minimal POC step. A full rewrite using compiled-policy OPA Wasm would also change the user's chosen evaluator integration and is not assumed approved.

The current CI proof remains intact: Go SDK CGI and embedded Go OPA work in actual Wasmer guests. The missing link is the selected guest's outbound integration. Deployment stays gated while the architecture choice is unresolved.
