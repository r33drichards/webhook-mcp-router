## Exact mismatch versus strongest candidate

Wasmer 7.5.0 preview1 exports socket accept/recv/send/shutdown, but not open/connect. Its `wasix_32v1` socket API includes protocol in open and packs address+port for connect. Therefore renaming dispatchrun imports alone would still pass wrong arguments/memory layout. No doomed dispatchrun HTTPS run is being substituted for this source-level finding. The existing WASIX Go fork calls the actual WASIX ABI and is the appropriate next experiment.

The pinned official MCP SDK declares Go 1.25.0; OPA 1.9.0 declares 1.24.6. Inspected SDK dependencies' minima do not exceed 1.25. Fork 1.25.5 satisfies those declarations. The current hosted fixture's `go 1.27.3` directive is an independent project constraint; any later SDK/OPA trial must explicitly adjust an isolated copy and set `GOTOOLCHAIN=local` to avoid silently replacing the patched compiler. No dependency downgrade or main toolchain switch has been made.

## Smallest meaningful validation and first runtime result

`.github/workflows/prior-art.yml` installs only the existing official fork release, verifies its published archive SHA256 `c728bcffd6536f38125a652ada1da814bcf46c8cae974a873ab8f402f8d95ed0`, then uses Wasmer 7.5.0. It compiles a standard-library-only probe and inspects module imports. Stages are TCP echo with host receipt, TLS with an explicit synthetic CA and hostname, rejection of unknown CA, rejection of wrong hostname, and HTTPS POST with exact host-observed nonce. Only loopback destinations are permitted; no `InsecureSkipVerify`, external event delivery or custom shim is used.

If linking or TCP fails, stop before TLS. If these pass, separately test DNS and the actual SDK/OPA dependency set, then managed Edge. Local Wasmer success must not be called an Edge pass. The fresh CA/key are ephemeral synthetic test fixtures, not production credentials. No hosted deployment is part of this probe.

## First execution: partial success, not an HTTP pass

[Run 40159283074](https://github.com/r33drichards/webhook-mcp-router/actions/runs/40159283074), commit `388929e93b71de771d7794fd1a19e9279a100175`, successfully installed the digest-verified fork and Wasmer7.5.0. Guest import inspection confirmed `wasix_32v1` socket calls. TCP echo, trusted TLS, unknown-CA rejection, and wrong-hostname rejection all exited 0. The standard `http.Client` POST exited 1 with `context deadline exceeded (Client.Timeout exceeded while awaiting headers)`. The sink reached its request handler but response writing encountered EOF after the client timeout. Full HTTP/Edge compatibility is not established. A bounded follow-up compares synchronous standard HTTP serialization over verified TLS; it is diagnostic only, not a replacement application transport.

## Follow-up execution: verified HTTPS wire works, standard Transport still fails

[Run 40159424461](https://github.com/r33drichards/webhook-mcp-router/actions/runs/40159424461), commit `e61da1e0f37b6dc79f195c09dd20b602323e0cd1`: TCP, trusted TLS, both negative certificate checks, and synchronous HTTP POST using standard `Request.Write`/`ReadResponse` over the verified TLS connection all exited 0. The host independently logged exactly 15 expected bytes. Standard `http.Client` POST still exited 1 awaiting headers; its complete body reached the host around timeout. This isolates the remaining failure to the standard Transport execution path; scheduling/polling is a hypothesis, not a proven cause. The synchronous diagnostic is not wired into the application as a custom adapter.

Existing-upstream-fix search: release commit `b97db7e0fc1a0886d87e36323b1a6e2f9c1fe75b` to HEAD `e5fdf0eb213144cf9114712461d569e78f95f6e5` adds only wasmer.toml, with no networking fix. No newer release or issue-provided fix was found. DNS, actual SDK/OPA on the fork, and managed Edge remain untested. Keep the ordinary application workflow and this exploratory workflow's results separate: prior-art workflow is honestly failing at standard HTTP, not marked green based on earlier stages.
